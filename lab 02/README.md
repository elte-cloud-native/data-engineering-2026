# Lab 2 - Authoring a data pipeline in Azure Data Factory

## Azure Data Factory overview

Azure Data Factory (ADF) is Microsoft's cloud-based data integration service. It lets you create data-driven workflows (pipelines) that move and transform data between many different data stores, at scale, without managing any infrastructure.

Key Components:
* Pipelines & Activities: A pipeline is a logical group of activities (copy data, run a data flow, call a notebook, etc.) that together perform a task.
* Linked Services: Connection information to external resources (like a connection string), e.g. to a storage account or a database.
* Datasets: A named view of data inside a linked service, e.g. a CSV file in a data lake or a table in a database.
* Mapping Data Flows: Visually designed data transformations. They are executed on Apache Spark clusters managed by Azure, so you don't have to write Spark code.
* Integration Runtimes: The compute infrastructure that runs the activities.
* Triggers & Monitoring: Run pipelines on demand, on schedule or on events, and follow their execution.

👉 In short: Data Factory is the "ETL/ELT engine" of Azure. The same engine is also used in Azure Synapse pipelines, and its next generation is Data Factory in Microsoft Fabric.

Perfect for building your first data pipeline!

## The scenario

We have a small data warehouse in an Azure SQL Database with a product dimension table (`dbo.DimProduct`).
The source system regularly exports the product list into a CSV file (`Product.csv`) in a data lake.

Our pipeline has to load the CSV into the dimension table:
* products that are not in the table yet have to be **inserted**,
* products that already exist have to be **updated** (upsert).

The table uses two different keys:
* `ProductAltKey` is the **business key** (the product ID from the source system, e.g. `AR-5381`),
* `ProductKey` is the **surrogate key**, generated by the data warehouse itself.

Overwriting existing rows with the latest values is called a **Type 1 Slowly Changing Dimension (SCD)** load.

```
 files/data/Product.csv ──┐
                          ├──> Lookup ──> Alter Row ──> dbo.DimProduct
 dbo.DimProduct ──────────┘   (match on    (insert or
                               business     upsert?)
                               key)
```

## Task 3: Create a pipeline with a data flow activity

1. Go back to the resource group, open the `adf-lab2-xxxxxxx` data factory, and click **Launch studio**.
2. In Data Factory Studio, select the **Author** page (pencil icon) on the left.
3. Next to **Factory Resources**, click **+** and select **Pipeline** > **Pipeline**.
4. In the **Properties** pane on the right, change the pipeline name to `Load Product Data`, then close the **Properties** pane.
5. In the **Activities** pane, expand **Move and transform**, and drag a **Data flow** activity to the pipeline canvas.
6. Under the canvas, on the **General** tab, set the **Name** of the activity to `LoadProducts`.
7. On the **Settings** tab, next to the **Data flow** property, click **+ New**.
    The data flow designer opens. In its **Properties** pane set the **Name** to `LoadProductsData`, then close the pane.
8. At the top of the data flow designer, turn on **Data flow debug**, keep the default settings, and click **OK**.
    Starting the debug cluster takes a few minutes, you can continue with the next steps meanwhile.

## Task 5: Add the transformations

### Lookup

1. Click the **+** icon at the bottom right of the `ProductsText` source and select **Lookup**.
2. Configure the lookup:
    - **Output stream name**: `MatchedProducts`
    - **Description**: `Matched product data`
    - **Primary stream**: `ProductsText`
    - **Lookup stream**: `ProductTable`
    - **Match multiple rows**: <u>not</u> selected
    - **Match on**: Last row
    - **Sort conditions**: `ProductKey` ascending
    - **Lookup conditions**: `ProductID` == `ProductAltKey`

The lookup works like a **left outer join**: it matches the `ProductID` column of the CSV file with the `ProductAltKey` column of the table.
If a product already exists in the table, the output row contains the values from both sources.
If the product doesn't exist yet, the columns coming from the table (including `ProductKey`) will be `NULL`.

### Alter Row

1. Click the **+** icon at the bottom right of the `MatchedProducts` lookup and select **Alter Row**.
2. Configure it:
    - **Output stream name**: `SetLoadAction`
    - **Description**: `Insert new, upsert existing`
    - **Incoming stream**: `MatchedProducts`
    - **Alter row conditions** (the expressions are *case-sensitive*, use the **+** button to add the second one):
        - **Insert if**: `isNull(ProductKey)`
        - **Upsert if**: `not(isNull(ProductKey))`

The alter row step defines the database operation for each row: new products (no surrogate key found) are inserted, existing products are upserted.

### Sink

1. Click the **+** icon at the bottom right of the `SetLoadAction` step and select **Sink**.
2. On the **Sink** tab, set:
    - **Output stream name**: `DimProductTable`
    - **Description**: `Load DimProduct table`
    - **Incoming stream**: `SetLoadAction`
    - **Sink type**: Dataset
    - **Dataset**: `DimProduct`
    - **Allow schema drift**: selected
3. On the **Settings** tab, set:
    - **Update method**: select only **Allow insert** and **Allow upsert**
    - **Key columns**: List of columns, `ProductAltKey`
    - **Table action**: None
4. On the **Mapping** tab, turn off **Auto mapping**, and keep <u>only</u> the following mappings (delete the others):

    | Input column               | Output column   |
    |----------------------------|-----------------|
    | `ProductID`                | `ProductAltKey` |
    | `ProductsText@ProductName` | `ProductName`   |
    | `ProductsText@Color`       | `Color`         |
    | `ProductsText@Size`        | `Size`          |
    | `ProductsText@ListPrice`   | `ListPrice`     |
    | `ProductsText@Discontinued`| `Discontinued`  |

    Notice that `ProductKey` is not mapped: the database generates the surrogate key for the new rows.

The complete data flow: `ProductsText` + `ProductTable` → `MatchedProducts` → `SetLoadAction` → `DimProductTable`.

## Task 6: Debug the data flow

1. Make sure that **Data flow debug** is turned on and the cluster is ready (green check mark).
2. Select the `DimProductTable` sink and open its **Data preview** tab.
3. Click **Refresh**. This runs the data through the data flow without writing anything to the database.
4. Check the result: there should be **one upserted row** (product `AR-5381`, marked with an upsert icon) and **ten inserted rows** (marked with a `+` icon).

If something is wrong, check the **Data preview** of the previous steps as well to find where the problem is.

## Task 7: Publish and run the pipeline

1. Click **Publish all** at the top, then **Publish**. Until you publish, your work is only saved in your browser session!
2. Close the data flow tab and go back to the `Load Product Data` pipeline.
3. Click **Add trigger** > **Trigger now**, then **OK**.

    > **Note**: A pipeline can also be triggered on a schedule or by events (e.g. when a new file arrives in the storage account).

4. Go to the **Monitor** page (gauge icon) on the left and check the **Pipeline runs**.
    Running the pipeline takes a few minutes because a new Spark cluster has to be started. Use the **Refresh** button to follow the status.
5. When the run succeeded, click the pipeline name, then the eyeglasses icon next to the `LoadProducts` activity to see the details: how many rows went through each step and how long it took.
6. Turn off **Data flow debug** on the **Author** page, it's not needed anymore.
7. Go back to the **Query editor** of the SQL database in the Azure portal, and run the query again:
    ```sql
    SELECT * FROM dbo.DimProduct ORDER BY ProductKey;
    ```
    The table should now contain 11 products, and `AR-5381` should have `Discontinued = 1`.

### Questions

* Run the pipeline again (**Trigger now**). How many rows will be in the table afterwards? Why is it important that a pipeline can be re-run safely (it is *idempotent*)?
* Change the price of a product in the table (e.g. `UPDATE dbo.DimProduct SET ListPrice = 99 WHERE ProductAltKey = 'BL-2036';`) and run the pipeline again. What happens? What information is lost with an SCD Type 1 load, and how would a Type 2 load keep it?
* Why do we need a surrogate key (`ProductKey`) if the source system already has a unique product ID?
